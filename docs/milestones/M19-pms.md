## Goal

Port EvidRise's performance management into learner_hu as a new `pms` Postgres schema.
Three pillars: a **KPI catalogue with a multi-stage approval workflow**, **quarterly
performance reviews**, and an **AI analysis** service that summarises a member's review
context (competence gaps, KPI trend, wellbeing, CPD) via the Claude API. Backend only;
frontend awaits mockups.

All seed/sample content is generic and name-free (no real people, no client name).

---

## Scope

### New app: `apps/pms` (schema `pms`)

**KPIs (with HoD → HR → Exec approval route)**
- `Kpi` — an active KPI definition (objective link by code, dept, owner member,
  definition, unit, baseline/target, cadence, weight, higher_better, status).
- `KpiProposal` — a proposed KPI moving through stages:
  `draft → hod_review → hr_alignment → exec_approval → active`, with `changes_requested`.
  On reaching `active` it creates/links an active `Kpi`.
- `KpiProposalHistory` — audit entry per transition.
- `KpiMeasurement` — actual value per (kpi, period) time series.

**Performance reviews**
- `ReviewCycle` — an org-wide quarterly window (draft/open/closed).
- `PerformanceReview` — one per (cycle, member): reviewer, status
  (draft/submitted/acknowledged), self/manager summaries, strengths, development areas,
  overall rating, and snapshotted competence/KPI/wellbeing scores.
- `ReviewObjective` — SMART objectives on a review (progress, status).

**AI analysis**
- `ReviewAnalysis` — one per review: the model id used, the input-context snapshot, and
  the generated summary / strengths / development / suggested actions, with status
  (pending/ok/failed). Generated by the Claude API; degrades gracefully with no key.

### Design decisions

| # | Decision |
|---|----------|
| P1 | KPIs/proposals/measurements/cycles are `company_only` (not personal). |
| P2 | `PerformanceReview`, `ReviewObjective`, `ReviewAnalysis` carry personal assessment → `manager_of_unit` RLS on a (denormalised) `member` column: the member and their line of managers + HR admins see rows; peers don't. |
| P3 | Strategy objectives are referenced by `objective_code`/`objective_title` text on KPIs rather than a separate versioned strategy model (kept out of scope). |
| P4 | Review context scores are **snapshotted** on the review at submit time (frameworks readiness + KPI attainment + latest wellbeing), not recomputed on read. |
| P5 | AI analysis uses the Claude API via `core` config; the key lives only in `backend/.env`. No key → analysis row saved with status `failed` and a readable message; never crashes a request. |
