## Confirmed issues and changes

1. **Company dashboard counted live places as recorded seats.** `company_dashboard()` summed every paid `SeatPurchase`, while the Seats page and allocations concern recorded offerings. A company with two recorded seats and three live places saw five seats available. Fixed the dashboard seat totals to filter `offering__delivery_type="recorded"`; spending still includes both types. Added an HTTP regression test.
2. **Stripe return notices could claim the wrong payment was confirmed.** Purchases and live bookings looked for *any* pending row. Another pending payment could keep a completed payment spinning, and an absent/failed target could display success. Checkout return URLs now carry the purchase or booking ID. Each page follows that row and shows a neutral status when it cannot verify success. Added a recorded checkout URL assertion.

## Open logic gaps

1. **Live group lifecycle can become stale.** The current database has a cohort marked `in_progress` whose only session is `completed`. The admin page shows session status but has no action to mark a session or group completed. The API permits free-form session and cohort status patches without a transition check. The admin report counts `confirmed` and `in_progress` cohorts as “Live groups running,” so that KPI can describe scheduled or already-finished training as running. This needs a defined completion rule and a tested admin workflow.
2. **Live certificates are blocked by configuration.** The existing `issue_live_certificate()` path intentionally raises `ConfigurationBlocked`; attendance and assessment criteria need a product decision before issuance can work.
3. **Refund amounts remain a manual staff decision.** The approval and processing path exists, but no automatic partial-refund formula is configured. This should be described to operators as manual policy, not assumed to be automatic.
