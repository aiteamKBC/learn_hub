- **Canonical eligibility:** Personal unlimited access now consistently requires a published, live, public course marked `in_subscription`. The access resolver, plan enrolment and console included-course count use this definition. Private company courses, drafts and deleted courses are not exposed by a personal subscription. Subscription access remains live-evaluated; it does not create a permanent purchase entitlement.
- **Plans and configuration:** New personal console plans are created as `unlimited_b2c`; their legacy course-list rows are neither used nor editable. Personal plan course views show the actual eligible catalogue. Team plan behaviour and its course/seat configuration remain unchanged.
- **Subscriber safety:** Learner subscription status and course enrolment no longer select one of multiple active personal plans arbitrarily. The account API reports the integrity issue for support review, while the access resolver may still establish access from any qualifying unlimited plan. Checkout rejects a live active/trialling/past-due subscription and safely reuses a current incomplete attempt with the same provider idempotency key; expired or asynchronously failed Checkout attempts are marked cancelled so they do not block a legitimate retry.
- **Financial reporting:** Overview, plan totals and revenue charts now count only stored invoices whose status is `paid`. Payment history continues to display each invoice's recorded amount and currency, so an older yearly £19.99 invoice is preserved as history rather than overwritten with the current plan price.
- **Validation:** This follow-up ran only the requested static checks (targeted Ruff, frontend TypeScript and `git diff --check`); no Django suite, browser automation, live Stripe request, migration, Neon write or email was run.

## Subscription checkout and access safeguards (2026-11-28)

- **Checkout contract and concurrency:** Personal subscription Checkout now calls the gateway's actual contract, including `trial_days` and a stable `subscription-checkout-<subscription-id>` idempotency key. A `select_for_update` lock on the existing learner record serializes first and concurrent attempts even when no subscription row exists yet. A current incomplete attempt is retried with that same key rather than creating another Checkout Session or possible charge.
- **Failure and expiry handling:** A known pre-provider `payments_unavailable` failure cancels its local incomplete record immediately. Other provider/network failures retain the record for a safe idempotent retry; stale, unlinked incomplete records are cancelled after the Checkout expiry window, and verified Stripe expired/asynchronous-failed events also cancel them. Active, trialling and past-due rows are filtered by their period end before duplicate detection.
- **Subscription enrolments:** `Enrollment.source=subscription` is no longer eligible for the legacy-purchase resolver path. Player and service-level course/lecture gates re-evaluate canonical live subscription access, including course eligibility, subscription expiry and `excluded_from_subscription`. A separate cash, token, admin or grandfathered right still wins through the resolver, so expiry never removes an independently purchased course, historical entitlement, progress or certificate.
